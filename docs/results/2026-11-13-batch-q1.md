## r6: committee re-run

R6 repeats committee_fix_c's configuration (3 agents, 3 groups, `stacks-ch4-phase1`, 10
generations) at a commit with the promotion and thinking fixes, to tell harness faults from the
model's own limits.

| | committee_fix_c | r6 |
|--|--:|--:|
| Tokens, 10 generations | about 5.6M | 1,738,649 |
| Tokens per generation | about 0.56M | 139K–216K (mean 174K) |
| Artifacts created | 71 | 30 |
| Verified in Lean | 10 (3 were the scribe's scaffold) | 2 |
| Generations 5–9 verifying anything | 0 of 33 | 0 of 15 |
| Novelty set on verified artifacts | 0 of 71 | 2 of 2 |

- **The harness faults are gone.** No scaffold verified; no foundation build failed or rolled
  back; no promotion was refused. The thinking fix cut tokens per generation about 3×, and 64% of
  tokens are now output.
- **Both tag closures went to the wrong statement.** Tag 0014 (*Functor*) was closed by
  `CategoryDef`, a renamed copy of the seeded `Category` (labelled N1 0.75). Tag 0015 (*Natural
  transformation*) was closed by a `Functor` (N0). In committee mode, a verified artifact closes
  whatever tag its group was assigned, without a check that it is that statement. Read correctly,
  the run produced one new definition (a functor, generation 9) and closed no tag. The progress
  line's "33%" includes the seeded tag.
- Because 0014 was closed early, generations 4–8 attempted natural transformations with no functor
  in the foundation. There `Functor C` resolves to Lean core's `Functor` (the monad class), which
  accounts for several "Application type mismatch" failures.
- **The planning panel put all three groups on one tag in every generation.** This goal's graph
  is a linear chain, so only one task is ever available. That is a known property of this goal,
  not a new fault; R7's goals have real edges.
- The other 28 failures are Lean errors against the from-scratch API: re-declaring `Category` (5),
  the bundled `(C : Category)` idiom (5), unknown identifiers (4), and syntax errors.
- The server ran at most 3 requests at a time, with a peak KV-cache use of 1.4% and 139 output
  tokens/s.

## arms: rehearsal of the Phase C arms (not Phase C)

On `stacks-kernel-track-b`, 2,000,000 tokens per arm. compare_arms ran over every pair. There is
nothing to compare: every arm verified 0 statements.

| Arm | Runs | Generations | Tokens | Over budget | Artifacts | Verified |
|-----|-----:|------------:|-------:|------------:|----------:|---------:|
| C9 | 1 | 7 | 2,223,347 | +11.2% | 21 | 0 |
| C9b | 1 | 6 | 2,143,492 | +7.2% | 18 | 0 |
| R9 | 1 | 6 | 2,373,776 | +18.7% | 18 | 0 |
| S1 | 1 | 17 | 2,120,215 | +6.0% | 8 | 0 |
| I9 | 8 of 9 | 2 each | 345,557 each | +55.5% per run | 1 each | 0 |

Why nothing verified:

1. **Two `Category` classes.** Goal files could not name a seed (`Goal.load` ignored the key), so
   the kernel tracks started from the shipped from-scratch `Category` class, although they tell
   agents to build on Mathlib. 52 of 73 artifacts imported both, and **24 failed with `failed to
   synthesize CategoryTheory.Category`**: the instance search mixed up the two classes.
2. **Made-up module paths.** 13 artifacts imported Mathlib modules that do not exist
   (`Mathlib.CategoryTheory.Category.Isomorphism`, `…NaturalTransformation.Basic`, …), which Lean
   reports as a missing object file. That is the model's error, not the environment's.
3. **The eight I9 runs were the same run.** Token for token: 11 calls, 294,028 prompt and 51,529
   completion tokens each. S1's first call matched them too. Requests carried no seed, so each
   freshly started server sampled from its engine seed in the same order. The I9 arm was one
   sample counted eight times. Its one artifact opened every docstring with `/--` and closed it with
   `/-`. The whole file was therefore a comment, and the artifact failed as contentless.
4. Budgets are checked when a generation starts, so each arm overshot by up to a generation. A
   single I9 generation costs more than its 222,222-token share.

## vLLM start-up hangs

4 of 18 TP=2 starts hung: jobs 412, 413, 418 and 427. All stopped after the same log line,
`[pynccl.py:148] vLLM is using nccl==2.30.7`, until vLLM's own 600 s engine timeout. Healthy starts
print the all-reduce backend choice a second later and answer in 70–80 s. Job 427 logged its
physical GPUs: **0 and 2**. The two earlier rounds that served logged **0 and 1**, which `nvidia-smi
topo -m` shows as `NV12`. H100 NVL cards are NVLink-bridged in pairs, so 0 and 2 have no bridge.
**Working hypothesis, untested:** TP=2 on an unbridged pair hangs while initialising custom
all-reduce or NCCL peer-to-peer over PCIe. The run script logged no physical GPUs, so the pairs
behind the other three hangs are unknown.

| Finding | Change | Where |
|---------|--------|-------|
| The kernel tracks seeded a second `Category` | Goal files name their seed; both kernel tracks start bare | PR stacked on #94 |
| Isolated runs sampled identically | Each run draws a sampling seed, records it, and sends a seed with every request | PR stacked on #94 |
| A start-up hang ended the job | The run script logs the physical GPUs and their links, and retries a hung start with `--disable-custom-all-reduce`, then without NCCL peer-to-peer | PR stacked on #94 |
