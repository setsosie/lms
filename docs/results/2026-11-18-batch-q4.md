## The one artifact built on prior work

In s3, generation 4 verified this definition of a category fibred in groupoids (Stacks 003T),
using `IsCartesianOverC` from generation 2:

```lean
structure CategoryFibredInGroupoids (C : Type u) [Category C] where
  S : Type v
  [inst : Category S]
  π : S ⥤ C
  is_fibred : ∀ {X Y : S} (f : X ⟶ Y), IsCartesianOverC π f
```

`IsCartesianOverC` is a faithful statement of 02XK (a cartesian morphism over C), though it
duplicates Mathlib's `Functor.IsStronglyCartesian`. Definition 003T has two conditions:

1. every morphism `V → U` in C with `U = p(x)` lifts to a morphism with target `x`;
2. every morphism of the fibred category is cartesian (lifts are unique in the strong sense).

The artifact encodes (2) only. Without (1), the empty category over C satisfies it. The tag and
the name are right (the statement in the goal file matches the live Stacks page word for word);
the gap is in the body. **D4 review (2026-11-18) gave it partial credit:** it covers the
definition's opening and condition (2), and it built on earlier verified work, but it does not
reach (1). The group's own notes claimed that (2) "encapsulates existence and uniqueness". It
does not.

If that artifact is set aside, the substantive read is **KEPT, NOT BUILT ON**.

Nothing in the loop could have seen the gap:

- **Status is binary.** The first verified artifact sets the tag done and the statement
  formalized. 003T then closed for good.
- **The reviewer never sees the statement.** It is shown the tag number and asked whether the
  code will compile. Nothing compares the code with the Stacks text.
- **D4 records novelty only** (N0–N3). It has no field for faithfulness or coverage.

## What failed

By first Lean error, over the 112 failed artifacts:

| First error | Artifacts |
|---|--:|
| An import of a Mathlib module that does not exist at the pinned Mathlib | 28 |
| Type and application mismatches | 22 |
| `⥤`, `⟶` or `≫` without `open CategoryTheory` (the notation is scoped, so it does not parse) | 19 |
| Unknown identifiers, constants and namespaces | 13 |
| Other parse errors | 12 |
| Instance synthesis | 8 |
| Unsolved goals and tactic failures | 3 |
| Other (universe levels, field notation, `sorry`, an unknown tactic) | 7 |

- The first and third rows are 42% of all failures, and both can be caught before Lean runs.
  The 28 artifacts import 21 distinct module names that the pinned Mathlib does not have, most
  often `Mathlib.CategoryTheory.Iso.Basic` (6 artifacts), `…NatTrans.Basic` and
  `…NaturalTransformation.Basic` (4 each).
- One use of a kept entry failed on the entry's shape. `CategoriesOverC` bundles `[inst : Category S]`
  as a field, so `Category F.S` is not found outside the structure.
- **None of the 120 artifacts uses Mathlib's `FiberedCategory` API**, although the goal's
  preamble tells agents to extend it rather than redefine it.
- **Every run spent most of its attempts on two tags that never verified.** 02XN was worked 39
  times and 0040 34 times across the four runs, with no verified artifact for either; 02XK was
  worked 28 times. Each run worked 4–6 tags of the 18 available at the start.

## What should change

| Finding | Proposed change |
|---------|-----------------|
| A statement closes on its first verified artifact, however much of it the artifact covers | Read each verified artifact against its statement, condition by condition, and let a statement covered in part stay open as PARTIAL, so the next group extends that artifact instead of closing the tag or losing the work |
| The reviewer sees a tag number and is asked only whether the code compiles | Show the reviewer the statement and the foundation, and don't adopt a MODIFY that drops `import LMS.Foundation` |
| 42% of failures are invented import paths or a missing `open` | Check imports against the pinned library's module list before calling Lean, and tell the agent |
| No artifact uses Mathlib's fibred-category API | Name the API's declarations in the goal or the prompt, not only in the preamble |
| A run uses at most 3 requests of its GPU | Run several runs per GPU, each in its own worktree |
